# Research: Current codebase state before planning training optimization runtime support

**Date**: 2026-05-17 20:55:51 +07+0700
**Researcher**: TheMetaSetter
**Git Commit**: 5012240e27ce4ad2b1ee613e3c328a4b26b685a2
**Branch**: dev

## Research Question

What is the state of the codebase immediately before writing the next plan for training optimization runtime support, with emphasis on data preparation, offline training, synthetic validation, evaluation, and checkpoint-monitor semantics as implemented today?

## Summary

The repository currently implements a configuration-driven offline anomaly-detection runtime centered on the SMD dataset, fixed-length window extraction, optional synthetic anomaly injection for multi-class auxiliary supervision, offline training entrypoints, and a separate evaluation path that reconstructs overlapping point scores back onto entity timelines. The codebase already contains recent runtime support for configurable optimizer selection, cosine scheduling at iteration level, gradient norm clipping, and explicit checkpoint monitor selection.

The most important state fact before planning is that the validation split used during offline training is created by slicing the original SMD training sequence and assigning zero-valued point labels to every validation timestep. Consequently, the newly added `val_vus_pr` metric is computed on a clean validation timeline rather than on synthetic validation windows, while synthetic validation currently contributes classification-oriented metrics such as `val_synth_roc_auc` and `val_synth_pr_auc`. There is no synthetic-validation VUS-PR path implemented at this time.

## Detailed Findings

### Data Preparation

- The active dataset builder for offline experiments is the SMD path in [src/data/loaders.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/data/loaders.py:108). The builder resolves the SMD root directory, parses the raw files, applies sequence cleaning, fits a standard scaler on the training split, transforms all splits, constructs `WindowDataset` instances, and returns both datasets and data loaders.
- The standardized batch contract is already in place. `WindowDataset.__getitem__()` returns a dictionary containing `x`, `point_labels`, `mask`, `timestamps`, and `meta`, where `meta` includes `dataset_name`, `entity_id`, `split`, `start_index`, `end_index`, and `window_size` [src/data/loaders.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/data/loaders.py:83).
- The SMD parser reads raw train, test, and `test_label` files and validates entity existence when `entity_ids` filtering is used [src/data/datasets/smd.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/data/datasets/smd.py:59). It splits each original train sequence into a training prefix and validation suffix according to `validation_split_ratio`, then assigns zero-valued `point_labels` to both of those splits [src/data/datasets/smd.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/data/datasets/smd.py:141). The test split alone receives anomaly labels from `test_label`.
- Window extraction is index-based and on-demand. The dataset stores `(sequence_index, start_index, end_index)` triples and materializes each window slice when requested, rather than precomputing all windows in memory [src/data/loaders.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/data/loaders.py:61).
- Synthetic anomaly injection is centralized in `SyntheticAnomalyInjector` and uses the RedLamp 11-family taxonomy as the active class surface: `spike`, `flip`, `speedup`, `noise`, `cutoff`, `average`, `scale`, `wander`, `contextual`, `upsidedown`, and `mixture` [src/data/augment.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/data/augment.py:22). The injector samples a contiguous subsequence per anomaly event and can emit either binary or RedLamp multi-class classification labels [src/data/augment.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/data/augment.py:35).

### Modeling and Training

- Offline training is orchestrated by `run_training_experiment()` in [scripts/train.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/scripts/train.py:193). This function seeds the runtime, registers models and datasets, builds the dataset bundle, instantiates the model from merged config, builds the optimizer and optional scheduler, and passes the resolved runtime into `Trainer`.
- Optimizer construction is now configuration-driven. `build_optimizer_from_experiment_config()` accepts `optimizer_name` values `adam` and `adamw` and defaults to `adam` when omitted [scripts/train.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/scripts/train.py:80). Online adaptation follows the same naming contract over a selected parameter group in [scripts/run_online_adaptation.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/scripts/run_online_adaptation.py:84).
- Scheduler construction now supports two runtime families. `reduce_on_plateau` still builds a PyTorch `ReduceLROnPlateau`, while `cosine` is treated as an arithmetic policy and does not instantiate a scheduler object [scripts/train.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/scripts/train.py:142). The cosine learning-rate computation is implemented as a CANDI-style fractional-epoch helper in the same file [scripts/train.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/scripts/train.py:112).
- The `Trainer` now steps cosine learning rates inside the training batch loop when `cosine_scheduler_config` is present [src/engine/trainer.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/trainer.py:355). It stores per-batch learning rates in memory and logs epoch-level summaries `optimizer_lr_start`, `optimizer_lr_end`, `optimizer_lr_min`, and `optimizer_lr_max` [src/engine/trainer.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/trainer.py:485).
- Gradient norm clipping is implemented after `loss.backward()` and before `optimizer.step()` when `gradient_clip_norm` is configured [src/engine/trainer.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/trainer.py:374). The trainer aggregates `gradient_norm_max`, `gradient_norm_last`, and `gradient_clipped_steps` at epoch granularity [src/engine/trainer.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/trainer.py:490).
- Clean validation and synthetic validation are still distinct runtime phases. `validation_step` runs first on the original validation windows, then `synthetic_validation_step` runs if the model exposes it [src/engine/trainer.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/trainer.py:408). ### Evaluation

- The pointwise evaluation path is implemented by `Evaluator.evaluate()` and always consumes `model.test_step()` outputs, specifically the `point_scores` field [src/engine/evaluator.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/evaluator.py:158). It merges overlapping window scores back onto full entity timelines using `start_index` and `end_index`, averages overlaps, concatenates the reconstructed per-entity scores, and computes pointwise metrics [src/engine/evaluator.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/evaluator.py:131).
- Threshold selection is quantile-based over positive-support scores when available. The evaluator derives a scalar threshold from the concatenated point scores and then computes pointwise `roc_auc`, `pr_auc`, `precision`, `recall`, `f1`, `fpr`, and optionally `vus_pr` when `vus_max_buffer_size` is configured [src/engine/evaluator.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/evaluator.py:23).
- The offline trainer now invokes the evaluator on `val_loader` once per epoch when an `evaluation` block is present, and prefixes the returned metrics with `val_` before checkpoint selection [src/engine/trainer.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/trainer.py:467). Because this call uses the clean `val_loader`, the emitted `val_vus_pr` is a clean-validation pointwise metric rather than a synthetic-validation metric.
- Synthetic validation metrics do not reuse the evaluator path. Instead, they are aggregated from classification logits and synthetic classification labels through `_aggregate_multitask_classification_metrics()`, which emits `roc_auc`, `pr_auc`, and related metrics under the `val_synth_` prefix [src/engine/trainer.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/src/engine/trainer.py:443). There is no code path that reconstructs synthetic point-score timelines and computes `val_synth_vus_pr`.
- The standalone evaluation script `scripts/evaluate.py` remains test-split oriented. It rebuilds the model from config, loads a checkpoint, then runs `Evaluator` on `data_bundle["loaders"]["test"]` and writes metrics, records, curves, and the resolved config into the output directory [scripts/evaluate.py](/Users/conquerormikrokosmos/Downloads/LAPTOP%20MAC/MYUNIVERSITY/%C4%90A%CC%A3I%20HO%CC%A3C%20QUO%CC%82%CC%81C%20GIA%20TPHCM/%C4%90H%20KHOA%20HO%CC%A3C%20TU%CC%9B%CC%A3%20NHIE%CC%82N/Khoa%CC%81%20lua%CC%A3%CC%82n%20to%CC%82%CC%81t%20nghie%CC%A3%CC%82p/bachelor-thesis-2026/scripts/evaluate.py:65).

## Pipeline Documentation

The implemented offline pipeline is as follows. An SMD entity sequence is parsed from raw text files, split into train, validation, and test sequences, cleaned, scaled from training statistics, and segmented into sliding windows. Each window is collated into the standard batch dictionary consumed by the models. During training, the selected model executes `training_step()` on original or synthetic-augmented windows depending on model logic. Clean validation runs through `validation_step()`, while synthetic validation, when available, runs through `synthetic_validation_step()` on the same `val_loader` after synthetic augmentation inside the model path.

At epoch end, the trainer aggregates scalar logs and classification metrics, optionally calls the overlap-aware evaluator on the clean `val_loader`, and records epoch-level runtime metrics such as the final optimizer learning rate, batch-derived cosine learning-rate summaries, and gradient clipping summaries. Checkpoint selection then compares the configured `checkpoint_monitor_metric` against the best value seen so far. This selection surface is now decoupled from plateau scheduler stepping, so a cosine run can request `checkpoint_monitor_metric: val_vus_pr` even though no metric-driven scheduler exists.

The standalone evaluation pipeline remains separate from training. It reconstructs full-entity point-score timelines from test windows and computes thresholded pointwise metrics together with VUS-PR when configured. This evaluation path is not currently reused for synthetic validation windows inside the trainer.

## Historical Context (from documents/)

The design documents establish the intended thesis framing: fixed-length windows, a thesis-facing hidden-state contract, continuous and discrete prototype branches, task-specific fusion, synthetic anomaly classification, and an online adaptation stage with a lightweight projector. The current repository already reflects several of these structural decisions, especially the standardized batch contract, model-per-file organization, synthetic anomaly taxonomy, and registry-driven scripts. However, the design documents describe target architecture and intended future capabilities more broadly than the currently implemented runtime.

Two specific alignments with the design context are already visible. First, the repository has preserved the readability-first separation between configuration, data construction, model files, and engine code. Second, recent runtime support additions move the training engine closer to the documented need for explicit and reproducible experiments by validating optimizer names, clipping settings, scheduler families, and checkpoint monitor metrics directly in config validation.

## Open Questions

- The code now allows `checkpoint_monitor_metric: val_vus_pr`, but the current SMD validation split is label-clean by construction. It remains ambiguous whether future plans should treat this as a placeholder metric, a signal to change validation data semantics, or a cue to add a synthetic-validation VUS path.
- Synthetic validation currently produces classification metrics such as `val_synth_pr_auc`, but there is no `val_synth_vus_pr` or equivalent pointwise metric over reconstructed synthetic timelines. Whether that metric should exist is not answered by the current implementation.
- The new experiment configurations for RedLamp MLP baseline currently request `checkpoint_monitor_metric: val_vus_pr`. In a short smoke run on the clean validation split, `val_vus_pr` was not a usable checkpoint-selection signal because the underlying validation labels were all zero. This behavior should be treated as an implementation fact to account for in the next planning step.
